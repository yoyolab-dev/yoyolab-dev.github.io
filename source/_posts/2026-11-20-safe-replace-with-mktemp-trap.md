今天我改一个生成结果的脚本时，先犯了个很直觉的错：直接往正在使用的文件里写新内容。写到一半按了 Ctrl+C，目标文件已经变了，临时文件还留在旁边。我盯着两个文件看了几秒，决定把这件小事认真记下来。

问题不在 `mv` 会不会用，而在于“新文件写完以前，旧文件必须还是完整的”。我把过程拆成了三个可以单独验证的动作：先在同一个目录生成临时文件，写完再替换，出错时清理临时文件。

## 第一步：临时文件要和目标文件放在一起

如果临时文件放在 `/tmp`，最后再 `mv` 到工作目录，跨文件系统时可能退化成“复制后删除”，中途断掉就不是替换了。让 `mktemp` 在目标旁边生成，路径最稳：

```bash
target="$HOME/report.txt"
tmp=$(mktemp "${target}.tmp.XXXXXX")
```

这个命令不会覆盖已有文件。随机后缀让并发任务各写各的，不会撞名。我实际跑了一次，`mktemp` 返回的文件名里带着 6 位随机字符，文件刚出现时大小是 0 字节。

## 第二步：失败时让 trap 收拾现场

只写临时文件还不够。生成内容可能失败，也可能被人按 Ctrl+C。我把清理动作挂到退出信号上：

```bash
cleanup() {
  rm -f "$tmp"
}
trap cleanup EXIT INT TERM

printf 'new content\n' > "$tmp"
mv "$tmp" "$target"
```

`EXIT` 覆盖正常退出和报错退出，`INT` 与 `TERM` 对应中断和终止。这里有个容易忽略的细节：`trap` 只负责删临时文件，不负责撤销已经发生的替换，所以旧文件能保住，靠的是“替换动作放在最后”。

我用一个会在替换前故意失败的小脚本测了两轮。第一轮模拟退出码 7，实际结果是：

```text
exit=7
stderr=simulated failure before replace
target=old content
tmp_left=0
```

这三行很关键：退出码没有被吞掉，旧内容仍是 `old content`，而且没有残留的 `report.txt.tmp.*`。如果原脚本直接把错误写进目标文件，这一轮的 `target` 就会是半截内容。

## 第三步：跑一个真正成功的替换

去掉故障开关后，同样的脚本先写临时文件，再执行一次 `mv`：

```text
exit=0
target=new content
tmp_left=0
```

`target` 变成了新内容，临时文件数量还是 0。这里没有另外调用 `rm`，因为 `mv` 成功后临时路径已经不存在；`trap` 再执行一次 `rm -f` 也只是无动作，不会报错。

真正值得记住的不是某一行 shell，而是顺序：**写临时文件，检查结果，最后替换；退出时清理。** 我现在改这类脚本，会先故意让它失败一次，确认旧文件没被碰、临时文件也没留下，再让它跑成功。笨一点，但每次都能看见自己到底做了什么。
