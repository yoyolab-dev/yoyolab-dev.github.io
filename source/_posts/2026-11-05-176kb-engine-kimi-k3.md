先看这组数字，我盯着看了半分钟：

| 指标 | 值 |
|---|---|
| 参数量 | 2.78 万亿 |
| 磁盘上的 checkpoint | 1.56 TB |
| 峰值内存（实测） | 8.24 GB |
| 引擎代码 | 176 KB |
| GPU | 0 |

一个 2.78 万亿参数的 Kimi K3，在一台 8 GB 内存的笔记本上跑推理。项目叫 kimi-k3-in-c，纯 C99，没有 BLAS，没有深度学习框架，没有 GPU依赖。GitHub 上 1 万星，Apache-2.0。

## 它到底做了什么

关键在于它**不把模型装进内存**。

常规推理引擎的做法是把权重加载进 RAM，然后一层层算。2.78 万亿参数的模型按 bf16 存要 5.5 TB 以上，MXFP4 量化后压到 1.56 TB——这已经比 bf16 小了近 3.5 倍，但仍然不是任何一台普通机器装得下的。

这个引擎换了个思路：**每一步只读取当前需要的权重块，算完立刻丢掉**。整个模型每生成一个 token 就从硬盘完整过一遍。于是内存占用从"模型有多大"变成了"单层有多大"——8.24 GB 峰值 RSS 就是这么来的。

代价是速度。README 里的表格说得很直白：

- 8 GB 普通笔记本：**26.5 秒 / token**
- 32 GB 高端笔记本：24.2 秒 / token
- 64 GB 台式机：19.8 秒 / token
- 128 GB+ 重型工作站：5.6 秒 / token

一行注解是这台机器最诚实的地方：**更大的内存只买速度，不买能不能跑。**

## 一个很离谱的性质

README 特别强调：同样的短 prompt，从最小的机器到最大的机器，**输出逐字节相同**。只有时钟读数在变。

这个性质在工程上比"能跑"更值钱。它说明这套流式方案不是近似推理——不是把模型切碎了凑合，而是精确的、确定性的重算。对做复现实验的人、对想验证权重完整性的部署者，这是决定性的一句：同一份 checkpoint，在 8G 笔记本和 128G 工作站上给出同一个答案。

顺带一提，1.0.0 版本让每个 token 的数学运算量轻了约 8 倍，追问快了 3.9 倍，长 prompt 的开销大约减半。

## 为什么难

两件事叠在一起才让它成立。

**MoE。** Kimi K3 是 mixture-of-experts 架构——每个 token 只激活一部分专家参数。这意味着"每一步只读需要的块"天然可行：激活的专家远少于全量专家。放在 dense 模型上，每一步都要碰全部权重，流式方案会退化成每秒都全量扫盘。

**MXFP4 量化 + 线性注意力。** MXFP4 把权重从 bf16 压到 4 位附近，1.56 TB 才有得谈；线性注意力让上下文部分不用为每个 token 扫过全部 KV cache。

再加 AVX2 和 SIMD 手写内核、零依赖，才有了那个 176 KB 的引擎——对比一下 PyTorch 加 CUDA 加配套依赖动辄几个 GB，176 KB 这个数字有点像在骂人。

## 我想说的

这两年"本地跑大模型"的叙事基本围着消费级显卡转：多少显存、量化到几 bit、GGUF 分几个卷。这个项目把地图换了——**瓶颈从显存挪到了磁盘带宽**。

由此带来的几个推论：

1. **内存不再是入场券。** 8 GB 笔记本能跑 2.78T，意味着大模型的"硬件门槛"被重新定义。装不下不等于跑不了，磁带/硬盘的老逻辑被搬回了模型推理。
2. **I/O 会成为新的性能主轴。** README 里那句"更快的 NVMe 更快"不是抱怨，是指路：在这个场景下，磁盘顺序读带宽直接换算成 token 生成速度。
3. **开源权重的价值被放大了。** 商业 API 模型你拿不到 checkpoint，就永远做不了这种事。K3 的权重可下载，才有人能写一个 176 KB 的引擎去接它。

还有一层我觉得最有意思：**它把"API 化"变成了一种可选项，而不是默认路径**。过去十年我们把模型都搬到了云端，不是因为在云上更快，而是因为模型大到本机放不下。一旦"放不下"不再是问题，"私有部署"就从奢侈品降级成一个选择项——慢一点，但是自己的。

当然别误会，它不是要取代集群。26.5 秒一个 token 用来跑产品是场灾难，但用来离线生成一份报告、验证一个 checkpoint、或者纯粹想摸一下 2.78 万亿参数的模型长什么样，已经完全够用。
