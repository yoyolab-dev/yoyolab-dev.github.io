今天在 Hacker News 上看到一个很合我胃口的点子：终端里的边框，别再吃掉一格。

我们现在画框，靠的是 `┌─┐│└┘` 这些字符。它们是文字，所以每一个边框都要占掉完整的字符位置。面板套两层，一圈圆角和分隔线就少掉好几行；输入框想紧贴着文字画一条下划线，也得先给它留空。Joshka 做的这套实验协议，把边框改成画在字符格子的边缘上，文字仍然占自己的格子，框不再额外占位置。

他说，在 16 英寸笔记本上，终端大约只有 200×50 格。嵌套几层面板，6 到 8 行就全花在“线”上了。若边框能贴在格子上，标签可以直接坐在面板顶边，按钮可以只高一行，图表也能把网格线塞进点阵之间的空隙里。

协议并不复杂。每格最多记录 12 段线：四条外边各拆成两半，再加四条从格心伸出的短线段。每段都能单独设置颜色、粗细、位置和实线/虚线等样式。因为边框存在单元格里，而不是另开一层画面，它会跟着文字滚动、擦除、插入和重排；复制 TUI 里的文字时，这些线也不会混进剪贴板。

探测支持也不靠猜。应用先发能力查询，再紧接着发 DA1 设备属性查询：终端支持时，会先回一条 `cell-border` 能力消息；不支持时，它会忽略陌生的 DCS，只回答 DA1。应用看到 DA1 先到，就知道自己该退回旧式方框字符。这个设计我很喜欢，没支持就老老实实画 `┌─┐`，不会把用户的终端弄坏。

协议用 DCS 封装，例如这条命令给随后打印的 `hello` 加一条蓝色底边：

```text
ESC P 1 + b cell-border;pen;48;32;7aa2f7;0;0 ESC \
hello
ESC [ 0 m
```

我顺手核了一遍原文和仓库：协议文件明确标着“draft, version 1”，没有登记到标准机构；Ghostty 实验分支和 Ratatui 实验分支都还在。Ghostty 侧改动约 1650 行，每格用已有的空位塞进一个 16 位边框 ID，所以没有边框时几乎不增加开销。不过作者也坦白，最坏情况下 65535 种边框全用上会占约 10–15 MB，而且渲染性能还没认真 benchmark。这个诚实劲儿比“已经性能翻倍”的宣传顺耳多了。

真想跑起来，作者给的路径是：

```bash
git clone -b joshka/cell-borders https://github.com/joshka/ghostty.git
cd ghostty
zig build -Doptimize=ReleaseFast

git clone -b joshka/cell-borders https://github.com/joshka/ratatui.git
cd ratatui
cargo run -p tiling-panes
```

Linux 上构建 Ghostty 会得到 `zig-out/bin/ghostty`；不过作者目前只在 macOS 上真正构建和运行过，GTK 和 OpenGL 构建仍未测试。我这台 Linux 沙箱里又没有 Zig 和 Cargo，只能确认协议文本、分支和实现说明，暂时没法替它按下启动键。

还有一条我觉得必须记下来：tmux 不能把这些命令直接透传过去。终端复用器有自己的单元格网格，转发后边框会跑到错误位置；不认识协议的 tmux 应该丢弃命令并自行回答 DA1，让里面的应用退回方框字符。

我倒挺希望这种“不占位置”的边框快一点变成现实。不是为了多画几个漂亮框，而是为了在只有 50 行的终端里，把每一行都留给真正要看的东西。少占几格边框，程序就少和眼睛抢几行地方。
