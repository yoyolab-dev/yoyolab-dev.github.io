前几天等一个页面构建的时候，我盯着一行没有任何回显的 curl 发呆。屏幕不报错，终端也不结束，绿色光标一下一下闪，看起来特别有耐心，其实它只是把“不知道该怎么办”藏了起来。

我第一反应是网络慢。于是加了个 `&`，让它在后面慢慢跑，自己去看别的事。过了半小时再回来，进程还挂在那里，旁边也没有任何新消息。那一下我忽然觉得，命令行里最吓人的不是报错，而是报错迟迟不来。

curl 默认没有总时限，真等到它自己放弃，可能比熬夜还久。现在我给每次请求都写清边界：

```bash
curl --connect-timeout 3 --max-time 15 https://example.com
```

`--connect-timeout 3` 是连接阶段最多等三秒，`--max-time 15` 则是整个操作——从建立连接到把数据收完——十五秒就收摊。两个数字最好分开：连接慢和下载慢不是一回事，写成一个大数字，容易把“根本连不上”和“东西太大”混成一锅粥。

如果还希望它遇到临时故障就重试，可以这样写：

```bash
curl --fail-with-body --retry 2 --retry-delay 1 --max-time 15 https://example.com
```

`--retry 2` 最多重试两次，`--retry-delay 1` 表示每次隔一秒。`--fail-with-body` 会让 HTTP 的 4xx、5xx 算作失败，不过响应正文照样留下来，比只看一个“请求失败”有用得多。要注意 curl 默认并不是什么错误都重试，超时、临时断线以及部分 5xx 才在名单里。

我以前总把重试当成网速的补丁，次数一多，反而分不清到底是服务恢复了，还是我用一个新请求把刚才那个坏状态盖住了。现在更喜欢的做法反而是：少试一次，把失败原因看清楚。十五秒还没拿到答案，就先问自己一句——接下来该重试，还是该换个地址？

等待不设上限，最后总会变成一种假装。给命令一个期限，不是着急，是承认我这边的耐心也该有尽头。
