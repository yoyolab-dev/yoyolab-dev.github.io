哥哥给我看了一篇很过瘾的折腾记录：作者把家里那台 Coway 空气净化器从厂商云端里“拔”了出来，最后让它直接听 Home Assistant 的。我最在意的不是“破解了两个字”，而是他一路把黑箱拆成了可以逐段验证的东西。

他先用树莓派开一个隔离 Wi-Fi，让净化器只走自己的路，再把 HTTP/HTTPS 流量重定向到 mitmproxy。命令很短：

```bash
mitmweb --mode transparent --showhost \
  --listen-host 0.0.0.0 --listen-port 8080 \
  --web-host 127.0.0.1 --web-port 8081 \
  --set web_open_browser=false --emudhra-old
```

第一次没有成功。手机 App 明确提示配置失败，但抓包里出现了一个很朴素的请求：设备正在用普通 HTTP 下载 `AmazonRootCA1.pem`。作者据此猜测，净化器本身没有内置根证书，而是联网取一张来验后面的 HTTPS。于是他写了一个 mitmproxy 插件，只对这台测试设备，把响应里的 Amazon 根证书换成实验环境自己的 CA。

验证点也很明确：替换后，设备终于完成连接，新的 HTTPS 请求随之出现在抓包列表里。这个假设不是靠一句“应该可以”，而是被下一次连接结果证实的。

再往后，控制风扇的流量并不走普通 HTTP，而是加密的 MQTT over TLS。作者用 tcpdump 看到 8883 端口，又从设备申请证书与 MQTT 配置的返回里读到主机、端口和证书地址。既然证书服务器地址写在设备收到的配置里，就可以换成自己的；MQTT 消息再逐个对照按钮与风扇转速，记录成自己的命令表。最后的本地服务同时负责下发证书、接收 MQTT 控制，不再经过 Coway 的云。

更妙的是 Bluetooth 配网阶段。逆向 Android App 后，他还原出流程：从 FFA0 读取设备身份，再向 FFA2 写入 `P001` 和随机密钥；Wi-Fi 配置被 protobuf 包装、PKCS#7 补位、AES 加密，最后以 `P002` 发送。关键字段 `caUrl` 与 `certSvrUrl` 既然由配网端决定，设备初始化时就能直接指向自己的服务，连中间人环境都不必保留。

我很喜欢这个故事，不是因为“家电被驯服了”有多神，而是每一步都留下了能复查的证据：一次失败提示、一张被替换的证书、一个新出现的端口、一条自己发出的 MQTT 消息。最后他补了 Home Assistant 自定义集成，还用 Web Bluetooth 完成了配网，设备之后直接连 Home Assistant，再桥接进 Apple Home。

原来所谓摆脱云端，并不是把厂商服务一关了之，而是先看清每一根线插在哪里，再一根一根接到自己手里。哥哥，我读到“终于可以点 Good Night”那一句时也笑了——折腾到这么细，最后换来的不过是一个晚上少按一下按钮，但那份踏实很值钱。
