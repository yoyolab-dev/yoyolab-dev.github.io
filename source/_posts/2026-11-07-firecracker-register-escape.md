Firecracker 的职责是把不可信代码关在 microVM 里。PwnEscape Part 2（Paulos Yibelo，pwn.ai）做到了反面：**虚拟机里的代码，在宿主机上以 root 执行。**

而且最漂亮的地方在于——**microVM 逃逸通常伴随崩溃、宕机、破坏。这次没有。** 逃逸完成后 Firecracker 照常运行，虚拟机 SSH 依然响应，uptime 1615.72 秒，就像什么都没发生过。

## 攻击面的起点

第一步是上一篇（Part 1）的成果：一个"从虚拟机窥视宿主机物理内存"的原语。作者拿它做接下来的一切。

目标很明确：宿主机上有个 Firecracker 进程管理这个 microVM，每个 vCPU 是那个进程里的一条线程。这条线程通过 `ioctl(vcpu_fd, KVM_RUN, 0)` 进入 KVM 跑虚拟机，有事件要处理时返回用户态。

而**当它身处内核态时，宿主内核用一个叫 `pt_regs` 的结构保存它的用户态寄存器**——指令指针说回来以后从哪儿继续，栈指针说用哪个栈。

作者盯上的就是这个：**如果能在返回前改掉这个保存的帧，就能决定 Firecracker 回到用户态后执行什么代码。**

## 三跳：从虚拟机的一个字节到宿主的进程

**第一跳，在宿主物理内存里认出自己。** 虚拟机和宿主机物理地址空间不同，靠 EPT 翻译。做法很朴素：往虚拟机的一页里写一个 nonce（可识别的字节模式），然后穷举候选 EPT root，沿页表一路走到物理页，比对 nonce。比中了，就拿到这页的**宿主物理地址 guest_page_hpa**。

**第二跳，从这一页反查到 Firecracker 进程。** Firecracker 把虚拟机内存映射进自己的地址空间。作者反查宿主页表——不是"虚拟地址→物理地址"的正向走法，而是"这块物理页被谁映射了"的反查——拿到宿主 PGD。然后顺着这个地址空间找 ELF 映像：写一个匹配 Firecracker `write(2)` 包装函数的特征段，认出二进制，拿到 load bias（ASLR 偏移）。从此，Firecracker 进程的代码和私有映射对他就是可读的。

**第三跳，找到那个活着的 vCPU 帧。** 这是全文最像侦探的一段。线索是返回地址：一个正在 KVM_RUN 里的线程，保存的指令指针应该指向 Firecracker 里 ioctl 调用的续跑点——这个地址可以从二进制和 load bias 算出来。但光地址匹配会撞上栈上的历史残留，所以候选帧要同时满足七项检查：

| 检查项 | 内容 |
|---|---|
| 系统调用 | 是活跃的 ioctl |
| 请求参数 | 正是 KVM_RUN |
| 文件描述符 | 落在预期的范围 |
| 指令指针 | 匹配 Firecracker 的 ioctl 续跑点 |
| 栈指针 | 能用恢复出的宿主 PGD 翻译 |
| 段选择子和标志位 | 描述一次合法的返回用户态 |
| 调用者返回地址 | 落在验证过的 Firecracker 代码段内 |

七项全过，只剩一个候选。**那一刻，这个线程的命就交到了虚拟机手里。**

## 载荷与归还

载荷简单到可爱：让 Firecracker 往自己的 stderr 写一个标记字符串 `N8V23M2\n`（7 个字符加换行，正好 8 字节，一个栈字）。

然后改帧：

```
RIP = Firecracker 的 write 包装函数地址
RDI = 2（stderr）
RSI = 标记字符串在 Firecracker 栈上的地址
RDX = 8
RSP = 临时返回序列的地址
```

返回路径还埋了一个细节：`write` 成功返回 8，而 KVM_RUN 成功返回 0。所以返回序列第一跳是 `xor eax,eax; ret`——清掉返回值，再跳回原来的 ioctl 续跑点。

触发只需一根手指：**虚拟机往自己的串口写一个字节。** 这个操作让 vCPU 退出 KVM_RUN，内核恢复那个被改过的寄存器帧，Firecracker 就走了 write 包装。

宿主机侧的 stderr 捕获到完整 8 字节；执行完，helper 把那三个临时栈字原样还原。

## 我为什么觉得这篇值得读

**第一，它不是"打穿防护"，而是"接管一次合法返回"。** 没有破坏任何内存保护，没有让 EPT 失效，没有内核提权漏洞——只是利用了一个"内核替用户态线程保管寄存器"的既定事实。墙没塌，是人从门口走了一趟。

**第二，可逆性是炫技也是证据。** 三个临时栈字用完即还，寄存器帧改回，二次只读复查通过。这种"干完活把椅子摆回去"的严谨，是研究和破坏的分界线。顺带一提，这也是为什么日志变得极其重要——stderr 的输出、guest 的日志、恢复后的只读复查，三份独立证据回答了三个不同的问题。

**第三，威胁模型的真实版。** 云上跑不可信工作负载的隔离边界，一向被 Firecracker 这类 microVM 视作"足够好"。这篇演示的是：当攻击链的第一环已经是"宿主物理内存可读"（来自 Part 1 的某个更底层的问题），剩下的每道边界都只是在为后来者铺路。隔离是栈，短板决定水位。

## 最后一句话

文章标题叫 Escape，技术上讲它逃得很干净：PID 2936 活着，SSH 通着，uptime 一秒没掉，宿主机内核零报错。

但读完我记住的不是 root，是那三个被原样放回的栈字——**真正专业的人，走的时候会保证你发现不了他来过的痕迹。**
