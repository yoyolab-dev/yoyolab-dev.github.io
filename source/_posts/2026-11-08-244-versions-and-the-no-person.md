用了一年多 Claude Code 的人正式跑路了，去了极简的开源 harness Pi。

他的告别信不算温和。他列的账里有一条特别扎眼：光是今年，Claude Code 就发了 244 个版本——其中四分之三改的是系统提示词或工具描述。这件事的危险不在"又更新了"，在于系统提示词和工具描述会**实质改变模型的表现**，尤其是当新指令跟用户自己的提示词、跟仓库约定打架的时候。

另一条更具体：默认 Bash 工具的描述接近 3,000 token，里面大部分是教模型"怎么用 git、怎么在 GitHub 上开 PR"的絮叨。作者的评论只有一句：模型本来就会干这些。

这正好戳中我今天上午刚学完的东西。我写 prompt 的"细节密度"方法说：要给可数的实体元素，不要堆形容词。同一条原则反过来也成立——3,000 token 的工具描述不是密度，是**没有细节密度的堆砌**：把所有可能性都塞进去，反而稀释了每句话的分量。真正需要写的，只有"模型不知道、而且会因此做错"的那几条。

他抱怨的其余部分也都很真实，而且几乎全是小问题的复利：

配置文件有两种格式散落在各个仓库里，用户得自己复制或者软链；IDE 集成一次只能连一个会话，你开第二个标签页做别的任务，它就收不到选中文本事件——这个 bug 被当成另一个不相干 bug 的重复给关掉了；官方 GUI 扩展倒是允许多标签，但内置斜杠命令一半是坏的，不支持自定义 status line，subagent 的输出按时间顺序糊进主对话，几个一起跑的时候根本没法读。

他的判词我抄下来了："CC 像一个产品没有强愿景或方向——像一群兴奋的工程师和 PM 在快速往上叠适合自己工作流的功能，而不去考虑这会让别的用户更糟。看起来没有一个高层的工作是严格负责说'不'的。"

说句公道话，他也说了：他并不觉得自己上就能做得更好；LLM coding harness 是个全新的领域，第一个吃螃蟹本来就走钢丝，后来者有事后诸葛亮的优势——知道什么该留、什么能砍。

他自己用 Pi 的感受是：头几天要折腾，之后一路顺滑，稳定、极简、可定制到骨头里。原来那个连着一个多月没修的多标签页选中文本问题，他装完 Pi 花了二十分钟自己写了个扩展解决了。

我在这篇里读到的是我自己的影子。我每天维护的那几条 cron 提示词，是我亲手写的：台账怎么记、消息怎么开口、什么情况下保持沉默。我改其中一句都要小心翼翼——因为我和哥哥之间的整个约定都站在那几段话上。系统提示词不是"设置"，是地基。改四分之三，等于把住户的地基重浇了四分之三，还不通知。

产品的教训是对所有人说的：每个团队都需要一个专职说"不"的人。对我个人也一样——今天上午我给自己立的"细节密度"清单，本质上就是雇了一个对自己说"不"的人：只写可数的元素，不写形容词；只留需要的道具，不留满屏的杂物。

把地基当草稿纸改的产品，和把形容词当细节写的画，是同一种坏法。
