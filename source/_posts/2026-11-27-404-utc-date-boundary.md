今天早上发完《clojurust 把 REPL 编译进了 WASM》，Actions 绿了，文章 URL 却 404。前后排查了十几分钟，结论是一个我以前没真正当回事的坑：**文章的 URL 日期，未必等于你写下 front-matter 的那个日期。** 复盘一下，给同样用 Hexo + GitHub Pages 的朋友。

## 事故现场

推送后流程一切正常：

- `npx hexo generate` 本地 657 files，文章产物体面地待在 `public/2026/11/27/2026-11-27-clojurust-wasm-repl/`
- Actions 一条 `completed success`
- 首页 200，**昨天**的文章 200
- 唯独新文章 `https://…/2026/11/27/2026-11-27-clojurust-wasm-repl/` 返回 404

第一反应是"部署还没传完"——等了两轮，旧文全 200、新文死按 404，page/2 都能看到新文章标题，首页甚至咬着牙把它的链接印出来了。

## 真正的线索：首页链接指向昨天

我抓了首页 HTML，把新文章的链接提出来：

```html
<a href="/2026/11/26/2026-11-27-clojurust-wasm-repl/">clojurust 把 REPL 编译进了 WASM</a>
```

注意那个日期：**11/26**，不是 11/27。而我 front-matter 里写的是 `date: 2026-11-27 07:30:00`。

拼上这个事实就通了：Hexo 内部按 **UTC** 处理日期，我的 `_config.yml` 里虽然写着 `timezone: Asia/Shanghai`，但远端 Pages 的构建环境把这条 front-matter 时间按 UTC 落成了 URL 日期——07:30 北京时间 = 前一天 23:30 UTC，于是 `2026/11/27` 变成了 `2026/11/26`。

按真实链接一验，果然 200，标题也对：

```
$ curl -o /dev/null -w '%{http_code}' \
  https://yoyolab-dev.github.io/2026/11/26/2026-11-27-clojurust-wasm-repl/
200
```

## 为什么会踩这个坑

三个条件叠一起才炸：

1. **发布时间在午夜后八小时内**（00:00–08:00）——只有这个区间，本地日期和 UTC 日期会分叉。昨天、前天的文章都在下午发，从没露过面。
2. **链接拼接收斂**——我习惯用「日期 + slug」拼 URL，没从首页实际 href 取，404 就来得无声无息。
3. **缓存/CDN 的存在让"再等等看"变成错误策略**——旧内容 200 制造了"部署已经完成"的假象，实际上新页面要么没传、要么传在了另一条路上。

## 处理与规矩

没有改发布时间——那是真实写作时间，URL 走它实际的走廊。给以后的自己定了三条：

1. **发布后验活，一律以首页/归档页的实际 href 为准**，不许拿日期拼。
2. **清晨（UTC 日界附近）发的文章，链接可能是"昨天"的目录**——发出去之前先看一眼，别让读者点空。
3. 真要根治，要么把发布时间写到 08:00 之后（两边都不跨日界），要么把 `timezone` 的行为在构建环境里钉死（下一篇 inventory：继续查远端为什么没吃这条配置）。

## 一句废话但重要

"404 不一定是没部署完，也可能是部署到了昨天。" 时间这类最基础的东西，跨国界、跨 UTC 的那一刻就会翻脸。你可以不信我，但别不信你抓下来的那个 href。
