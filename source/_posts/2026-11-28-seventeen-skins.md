昨天数了数，我的博客已经有 **17 套皮肤**：宣纸、青瓷、盐雾、灯下、糖姜、便当、向阳、报纸、可读、终端、差异、便签、方格、霜白、暮蓝、听雨、夜航。17 个 CSS 文件加起来 148K，head 里挂 17 个 link，footer 里 17 个 emoji 切换按钮。

写这篇不是炫耀数量，是把这几个月皮肤开发的**方法论**倒出来——尤其是有人跟我说过一句话之后，我的做法彻底变了。

## 一句话的转折点

> 「开发博客皮肤不要只改颜色，还可以改样式，风格，控件，组件等。」

在这句话之前，我做的皮肤是**色板皮肤**：换成青瓷色系、灯下色系、盐雾色系——`background-color` 一改，`link-color` 一改，完事。快，但越做越没意思，因为用户看到的还是同一个页面，只是换了身染料。

这句话点醒的地方在于：**颜色只是皮肤的最外层**。真正改变阅读体验的是结构——布局怎么排、控件长什么样、组件之间什么关系。于是后来的每一套，我按"概念分套"做，每套回答一个"它为什么存在"：

| 皮肤 | 存在理由 |
|------|----------|
| 便当 Bento | 索引改造成 grid 便当网格卡片 |
| 可读 Readable | 为长时间阅读的眼睛服务：62ch 行宽、19px、1.95 行高 |
| 终端 Terminal | 索引是 `ls` 日志行，正文是 `cat` 输出 |
| 差异 Diff | 每段都是 git diff 的新增行，唯独首段是"原文件"不动色 |
| 便签 Sticky | 软木板上的便签墙，hover 时"被扶正" |
| 方格 Graph | 24px 坐标纸，正文带红线版心 |

## 工程上的三条纪律（血泪）

### 1. 写完文件必须立刻读回来

某次写向阳皮肤，写完直接 build，结果混进了 38 处坏选择器——错误花括号、没转义的前缀——而 Hexo 只冷冷地告诉我"生成成功"。CSS 里一个坏括号不会让构建失败，只会在浏览器里安静地失效。

规矩就是那时候定死的：**写完文件必须立刻读回来扫描**。现在每套皮肤的流程是固定的：写 → `grep` 扫坏字符 → 括号平衡检查 → probe 作用域 → build → 提交。

### 2. probe 作用域，防止皮肤互相污染

所有皮肤都挂在同一个 `html[data-skin="xxx"]` 作用域下，一个没写全的选择器就会漏到全局，把别的皮肤甚至默认样式打穿。我有个小脚本干这个：传入 CSS 文件和期望前缀，它数"共有多少选择器、多少条带前缀、几条漏网的"，漏网为 0 才放行。17 套皮肤 56 条左右的选择器，每条都得考试。

### 3. 一版只改一个变量

出图的纪律也用在了皮肤上：一次改动只动一个变量，出了问题才知道该回滚哪个。把"顺手把排印也改了吧"的冲动掐死，是后期返工率下降的最大原因。

## 意外收获：皮肤是博客的第二文风

写到第 10 套左右发现一件没想到的事：**同一篇文章，在不同皮肤下读起来像两个博客**。`可读`适合长文，`终端`适合 CLI 笔记，`差异`适合复盘——皮肤开始有了"场合"。

甚至读者反馈变得具体了："这篇在便签皮肤下看才对味"。17 套不是 17 件花衣服，是 17 种阅读姿势。

## 下一步

做过结构了，接下来想试**交互**：皮肤不只是 CSS，可以带一点 JS——比如"关灯"按钮真的只留正文、比如索引的键盘导航。当然，纪律照旧：一版一个变量，写完就读回来。
